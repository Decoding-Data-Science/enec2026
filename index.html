Setup notebook — core code
00_Setup_Nuclear_Enterprise_360.py
CATALOG = spark.sql("SELECT current_catalog()").first()[0]
SCHEMA  = "nuclear_enterprise_360"
VOLUME  = "training_files"
spark.sql(f"CREATE SCHEMA IF NOT EXISTS `{CATALOG}`.`{SCHEMA}`")
spark.sql(f"CREATE VOLUME IF NOT EXISTS `{CATALOG}`.`{SCHEMA}`.`{VOLUME}`")
VOLUME_PATH = f"/Volumes/{CATALOG}/{SCHEMA}/{VOLUME}"
DB_PATH     = f"{VOLUME_PATH}/nuclear_enterprise_360_v2_2_clean.db"

# Convert every SQLite table into a managed Delta table (repeatable: overwrite)
with sqlite3.connect(DB_PATH) as con:
    table_names = [r[0] for r in con.execute(
        "SELECT name FROM sqlite_master WHERE type='table' "
        "AND name NOT LIKE 'sqlite_%' ORDER BY name").fetchall()]
    for t in table_names:
        pdf = pd.read_sql_query(f'SELECT * FROM "{t}"', con)
        pdf = pdf.astype(object).where(pd.notnull(pdf), None)
        (spark.createDataFrame(pdf).write.format("delta")
              .mode("overwrite").option("overwriteSchema", "true")
              .saveAsTable(f"`{CATALOG}`.`{SCHEMA}`.`{t}`"))

spark.sql("ALTER TABLE document_chunks SET TBLPROPERTIES (delta.enableChangeDataFeed = true)")

Why so perfect?

The synthetic labels are cleanly separated by vibration (the V2.1 rule: anomaly when vibration ≥ 5.0 or temp ≥ 62.0). Real-world anomaly detection usually will not score 100%.

A critical ML lesson — class imbalance

1,797 Normal vs 23 Abnormal → only 1.26% abnormal. A useless model that always predicts NORMAL still scores ~98.7% accuracy. For rare events ask: did we catch the abnormal cases (recall)? How many alarms were false (precision)? How do both classes perform (confusion matrix / balanced accuracy)?

import sqlite3, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier, plot_tree
from sklearn.metrics import accuracy_score, confusion_matrix

conn = sqlite3.connect(DB_PATH)
df = pd.read_sql_query("""
    SELECT reading_timestamp, asset_id, vibration_mm_s, anomaly_flag
    FROM sensor_readings WHERE asset_id = 'A-001'
    ORDER BY reading_timestamp""", conn)

X = df[["vibration_mm_s"]]          # feature
y = df["anomaly_flag"]              # target: 0 normal, 1 abnormal

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.25, random_state=42, stratify=y)

model = DecisionTreeClassifier(max_depth=1, random_state=42)
model.fit(X_train, y_train)
pred = model.predict(X_test)

print("Accuracy:", accuracy_score(y_test, pred))
print(confusion_matrix(y_test, pred))      # [[449 0] [0 6]]
print("Learned split:", model.tree_.threshold[0])   # ≈ 5.0065

Step 1 — visualise the history · daily mean of hourly vibration (25 Aug 2025 → 25 Aug 2026)

A long stable period followed by a clear increase near the end of the year. Order matters — we cannot randomly shuffle time-series observations.

1 · Trend

The longer-term direction. Is vibration generally moving up, down or staying stable?

2 · Seasonality

Patterns that repeat at regular intervals. For hourly data, test a 24-hour pattern.

3 · Lag

A previous value used to predict the future: 1 hour ago and the same hour yesterday.

Mental model

Future sensor value ← recent history + yesterday’s pattern + operating context.

Step 2 — feature recipe (58 inputs)
  • Lag 1 h — what happened immediately before?
  • Lag 24 h — same hour yesterday
  • Rolling 24 h mean — what has been typical across the last day?
  • Time features — sin/cos of hour-of-day and day-of-week

6 signals × (lag1 + lag24 + roll24) = 54, plus 4 cyclical time features.

Step 3 — Ridge regression + recursive forecast

Ridge = regularised linear regression: simple, fast, explainable and stable when sensors are correlated. The model predicts all 6 signals for the next hour, then feeds the prediction back in and repeats hour-by-hour until 168 hours.

Step 4 — validate honestly (chronological split)

Train on earlier history; test on the last 7 days. Never randomly shuffle time series. Compare against a simple baseline first: “the next hour will look like the same hour yesterday.”

What is a Large Language Model?

A model trained to predict and generate sequences of language

Promptinstructions + question
Tokenstext broken into units
Modellearned patterns
Next-token probabilitieslikely continuations
Responseone token at a time
It learns patterns

Words, concepts, relationships, code structures and common language patterns from very large corpora.

It receives context

Your prompt + system instructions + conversation + retrieved documents + tool results.

It generates output

One token at a time, choosing likely continuations given the context. This is why it can be fluent and still wrong.

Simple mental model

An LLM is a powerful language engine — not a database of guaranteed facts.

A useful mental model — not a strict two-box taxonomy

Embeddings — useful mental model

An embedding turns text into a numeric vector so semantically related text can be compared — even when exact words differ.

meaning → vectors
"How much annual vacation do employees receive?"
   → embedding model → [0.021, -0.14, 0.51, …]

"Employees receive 30 calendar days of annual leave."
   → embedding model → [0.018, -0.13, 0.49, …]   ← close!
Non-negotiable rule

Document vectors and query vectors must use the same model and the same dimensionality. A 512-dim query cannot be compared with 1024-dim document vectors.

Cosine similarity in NumPy
retrieve()
vector_store = create_embeddings([c["text"] for c in chunks])
vector_store /= np.linalg.norm(vector_store, axis=1, keepdims=True)

def retrieve(question, top_k=4):
    q = create_embeddings([question])[0]
    q = q / np.linalg.norm(q)
    scores = vector_store @ q           # cosine = dot of unit vectors
    best = np.argsort(scores)[::-1][:top_k]
    return [(chunks[i], float(scores[i])) for i in best]

Retrieval strategies
Lexical · TF-IDF / BM25

Strong for exact terms, IDs and procedure language (“HR-2026-117”). Easy to explain and debug. Can miss synonyms.

Semantic · embeddings

Strong for paraphrases and concept similarity. Can retrieve conceptually similar but non-authoritative content.

Hybrid · combined

Balances lexical and semantic signals with enterprise metadata. Best for mixed enterprise query styles.

score = 0.80 × bm25 + 0.15 × authority + 0.05 × entity

def split_text(text, chunk_size=1200, overlap=200):
    text, chunks, start = " ".join(text.split()), [], 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append(text[start:end])
        if end == len(text): break
        start = end - overlap
    return chunks

client = get_deploy_client("databricks")
def create_embeddings(texts, batch_size=8):
    vecs = []
    for s in range(0, len(texts), batch_size):
        r = client.predict(endpoint=EMBEDDING_MODEL, inputs={"input": texts[s:s+batch_size]})
        vecs.extend(i["embedding"] for i in sorted(r["data"], key=lambda i: i["index"]))
    return np.array(vecs, dtype="float32")

def select_skill(question):
    q = question.lower()
    if any(t in q for t in REVIEW_TERMS):
        return "reliability_review"
    if any(t in q for t in PROCEDURE_TERMS):
        return "approved_procedure"
    return "asset_summary"

Capstone scenario

An engineer has observed unusual behaviour around synthetic Asset A-001. Your team must prepare an evidence-backed condition/reliability review using the available enterprise data and knowledge.

Capstone question

What does the available evidence say about A-001, what should a qualified reviewer pay attention to, and what is the appropriate human next step?

Required evidence
  • Structured enterprise data
  • Recent sensor trend and/or ML output
  • Approved document guidance
  • Work-order / inspection / field context where relevant
  • Clear provenance and source identifiers
  • Evidence gaps, conflicts and uncertainty
Boundary — the output is decision support

The application may prepare evidence and a review briefing. It must not diagnose a real physical failure, issue control commands, authorise maintenance, close work orders, treat a model output as approval, or approve its own recommendation.

Capstone workflow
  1. Understand and restate the business question.
  2. Inspect the relevant structured data.
  3. Review the recent sensor trend and ML/forecast output.
  4. Retrieve relevant enterprise documents.
  5. Confirm which procedure/policy is currently authoritative.
  6. Combine evidence without blurring source types.
  7. Identify conflicts, limitations and missing evidence.
  8. Prepare a bounded review briefing.
  9. Stop at the human-review boundary.
  10. Prepare a concise team demonstration.
